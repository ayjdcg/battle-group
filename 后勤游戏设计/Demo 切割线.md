# 后勤游戏 · Demo 切割线

> 配套文件：`机制库.md`（完整机制记录）。
> 本文件只回答一件事：**demo 做什么，不做什么。**

---

## 一、Demo 只需要验证一句话

> **玩家明明只是在分配运力，却感到紧张，并且会为某个决定后悔。**

这句成立，游戏就成立，剩下的全是加法。这句不成立，加再多机制也救不回来。

**任何不服务于这句话的机制，一律后置。** 下面的所有取舍都由这把尺子量出来。

---

## 二、进与不进

### 进（缺一不可）

| 机制 | 为什么必须留 |
| --- | --- |
| 边的吞吐与在途延迟 | 稀缺与延迟的来源，没有它就没有题 |
| 阶梯式短缺 | 取舍的来源。线性衰减会让平均分配成为最优解 |
| 三种物资的可逆性差异 | 否则它们只是三个名字不同的同一种东西 |
| 随姿态变化的消耗 | 压力的节奏来源 |
| **战斗提前三天预告** | 它就是核心循环本身 |
| 配额式命令 | 操作体验的生死线 |
| 带延迟的信息 | 紧张感的主要来源 |
| **师 AI：姿态状态机 + 性格四参数** | "后悔"来自你误判了人。砍掉它，demo 就验证不了核心乐趣 |
| 战报归因 + **反事实提示** | "后悔"的直接来源，且便宜得过分 |

### 不进（记在机制库里，等 demo 验证通过再说）

| 机制 | 为什么可以砍 |
| --- | --- |
| 人员四分（军官/军医/娱乐家） | 只是让取舍的**种类**变多，核心取舍没有它们也已成立 |
| 伤员轻重分档、装备回收 | 同上 |
| 拥堵非线性、中转装卸 | 同上 |
| 节点囤积风险 | 同上 |
| 观察稀缺（通信投资、盯人名额） | demo 用固定延迟即可 |
| 向上级申诉 | 后期增味 |
| 假消息 / 信任经济 | 已明确暂缓 |
| 反后勤（空袭、破路） | 可作为脚本事件出现，不做成玩家要管理的系统 |

## 三、Demo 规格

### 地图

一张**固定**地图（不做随机生成）：

- 后方基地 ×1（物资无限，瓶颈只在运力）
- 中转节点 ×2
- 前线节点 ×3
- 铁路 ×1（吞吐大、在途短、脆弱）
- 公路 ×2（吞吐小、在途长、韧性强）

### 部队

3 个师。每个师：

- 状态数：兵员满编率、弹药储备（天）、给养储备（天）、疲劳度、装备完好率
- 性格：激进度、囤积倾向、服从度、自知力
- 三个师的性格刻意拉开，做成**冲锋型 / 铁公鸡 / 老实人**

### 物资

3 种：**弹药、给养、人员**。人员**不**细分。

### 时间

按天推进。一局 30 天。目标：撑住 30 天不崩。

### 命令

玩家每天能做的只有四件事：

1. 调整各条线路的物资配比
2. 调整各师的补给优先级
3. 设置各师的最低储备线
4. 回电（告知真相，影响该师的姿态决策）

**没有手动发车。**

### 信息

- 统一延迟 1–2 天（不做按师区分）
- 数值按"充足 / 尚可 / 紧张 / 告罄"分级显示
- 不做失联

### 界面

一屏够用，核心是**监护仪面板**：

- 一行一个师：效能条、三种物资剩余天数与下降箭头、数据的"最后更新时间"
- 交战中的师高亮
- 在途车队图标 + ETA
- **必须有的一行**：物资耗尽时刻 vs 车队 ETA 并排对比
- 每日战报：带后勤归因 + 反事实提示

## 四、数值起点

**这些数字一定是错的**，它们只是让程序先跑起来的起点。真正的数值靠试玩磨出来（一局十分钟，可以磨很多次）。

### 消耗倍率

| 姿态 | 倍率 |
| --- | --- |
| 休整 | 0.8 |
| 底噪（固守） | 1.0 / 2.0 |
| 蛰伏 | 1.2 |
| 积极防御 | 3.0 |
| 进攻 | 6.0–8.0 |

单个高强度交战日额外吃掉约 3 天的量。

### 弹药档位（阶梯）

| 储备 | 战斗力系数 | 附加 |
| --- | --- | --- |
| ≥50% | 1.0 | — |
| 50%–20% | 0.7 | 失去主动进攻能力 |
| 20%–5% | 0.35 | — |
| <5% | 0.1 | 连续 3 天则失去建制 |

### 效能公式

```
效能 = 满编率 × 弹药档位 × 装备完好率 × (1 - 疲劳)
```

（demo 不含军官系数。）

### 运力

关键约束：**总运力约等于三个师全部处于"积极防御"时的消耗量。**

也就是说——三个师同时打防御，刚好供得上；只要有一个师转入进攻，就必然有人要挨饿。这是"永远不够"的刻度起点。

### 其他

- 铁路：日吞吐 100，在途 1 天
- 公路：日吞吐 40，在途 2 天
- 信息延迟：1 天（交战中的师 2 天）
- 战斗预告：提前 3 天

## 五、每日主循环（实现顺序）

```
1. 推进日期
2. 在途队列前进，到期批次入库
3. 每个师跑五步：感知 → 决策姿态 → 生成请求 → 消耗执行 → 上报
4. 有交战的师进行结算，移动战线
5. 按玩家配额从基地发出新批次（含回程）
6. 生成战报（含归因与反事实）
7. 更新玩家可见的延迟快照
```

七步，预计两三百行。

## 六、验证标准

demo 做完后，自己玩十局，逐条对照：

- [ ] 有没有出现过"我明知道他要完了，但车赶不到"的时刻？
- [ ] 有没有为某一趟车发错了人而后悔？
- [ ] 三个师的性格，玩到第三局能不能被认出来、并针对性对待？
- [ ] 有没有出现过"喂饱了他，结果把他喂死了"？
- [ ] 有没有出现过"这次我故意不给他，把他钉住"？
- [ ] 战报能不能让人明白**是我的哪个决定导致了这个结果**？

第一条和第二条是及格线。后四条命中任意两条，这个项目就值得继续做下去。

如果十局下来一条都没命中，问题多半出在**运力的刻度**上（太松），而不是机制不够——先调运力，不要急着加机制。

## 七、不要做的事

- 不要在 demo 验证通过前，从机制库里往回搬任何东西。
- 不要先写完整的数值表再实现。
- 不要做地图随机生成。
- 不要做美术。仪表盘用纯文字和方块条即可。
- 不要做存档、设置、主菜单。
