## 三、地图与运输线（固定数据，不写生成器）

`Demo 切割线.md` 三、Demo 规格 / 地图：后方基地 ×1、中转节点 ×2、前线节点 ×3、铁路 ×1、公路 ×2。**这是一张写死的常量，不需要 `map-generator.js` 那种随机生成器**，因为该生成器的校验规则（20–32 个节点、三线战斗地形、专供自动战斗用）跟这张 6 节点小图完全不匹配，硬套反而增加复杂度。

`机制库.md`「系统 1」讲的"边的四属性"（吞吐、在途天数、脆弱度、载荷）是**运输线级别**的属性，不是逐段路口的属性——demo 里中转节点不单独占用吞吐或装卸时间（拥堵非线性、中转装卸明确不进 demo，见 `Demo 切割线.md` 表格），中转节点只在战报文案里出现（"车队经过中转站 A"），不参与任何数值计算。据此把"1 铁路 + 2 公路 + 2 中转 + 3 前线"钉成三条运输线：

## 四、核心状态结构（`GameState`）

这是整局唯一的数据源，UI 只读它、玩家指令只改它的 `orders` 字段、`advanceDay()` 是唯一允许推进它的函数。字段名以后写代码时不要改，改了要同步改这份文件。

  ended: false,

  base: {

  },

  personnel: {
    pool: 0,                 // 人员池：新兵与康复老兵共用，等待分配的人数（demo 用抽象人数单位，见第五节）

    trainingQueue: [],       // [{ id, count, track: 'urgent'|'normal', arrivesDay }]
    hospitalQueue: [],       // [{ id, count, arrivesDay, overflowDays: 0 }]

  divisions: [
    {
      id: 'div-1', name: '第一师',
      personality: { aggression: 0, hoarding: 0, obedience: 0, selfAwareness: 0 }, // 0~1，见第五节三种性格预设
      posture: 'defend',           // 'attack'|'active-defend'|'defend'|'dormant'|'refit'|'retreat'

      fatigue: 0,                  // 疲劳度 0~1

    // div-2, div-3 同构

  orders: {                  // 玩家当天下的指令，advanceDay() 读取后清空/保留到下一次修改

    divisionPriority: { 'div-1': 1, 'div-2': 1, 'div-3': 1 }, // 相对优先级权重，运力不够时按此分配

    personnelAssignment: {},        // { 'div-1': count, ... } 本轮从人员池分给谁

  },

  battlePreview: [],          // 战斗预告：[{ divisionId, day, source: 'orders-known'|'enemy-signal', certainty }]
  eventLog: [],                // 每日战报，UI 从这里读历史

**关于"抽象人数单位"**：`机制库.md` 没给人员池的具体单位（是"人"还是"编制百分比点"）。`Demo 切割线.md` 数值起点里医院日处理名额写的是"1 D 对应人数的 20%"，说明人员也换算到与 D 相关的一个抽象单位上。本文件的暂定选择：**把一个满编师定义为 100 点满编，`manpowerRatio` 就是这 100 点里还剩几成**；人员池、训练队列、医院队列全部用"点数"计数，1 点 = 1% 满编。这样"1 D 对应人数的 20%"就能直接读成"20 点"，不用引入第二套换算表。这是本文件做的补充假设，不是设计文档原文，如果后续设计文档给出了明确单位，以设计文档为准并回来改这一段。

## 六、每日主循环九步：函数签名 + 伪代码

对应 `Demo 切割线.md` 五、每日主循环（实现顺序），一步一个函数，`advanceDay(state)` 按顺序调用它们，不要合并、不要打乱顺序（顺序本身是设计——例如"配额结算"必须在"师的请求"之前，否则师看到的库存是昨天的）：

```js
function advanceDay(state) {
  state.day += 1;                          // 1. 推进日期
  settleQuota(state);                      // 2. 配额结算
  settleMobilization(state);                // 3. 国家动员结算
  advanceQueues(state);                     // 4. 在途/训练营/医院队列前进
  for (const division of state.divisions) {
    perceive(state, division);              //   5a. 感知（带自知力偏差）
    decidePosture(state, division);         //   5b. 决策姿态（性格加权规则表）
    const request = generateRequest(state, division); //   5c. 生成请求（含囤积/抢运力放大）
    consumeAndApplyPosture(state, division); //   5d. 按姿态消耗
    autoAllocateArrivedCargo(state, division); //   5d'. 前线自行分配（见系统 5）
    reportUp(state, division);              //   5e. 上报（精度由延迟决定）
  }
  resolveBattles(state);                    // 6. 交战结算：移动战线、产生战斗减员、按比例分流
  dispatchShipments(state);                 // 7. 按玩家配比/优先级/今日上限发出新批次
  generateDailyReport(state);               // 8. 生成战报（含归因 + 反事实）
  refreshInfoSnapshot(state);               // 9. 更新玩家可见的延迟快照与配额预告
  if (state.day >= GAME_LENGTH_DAYS) state.ended = true;
}
```

以下每个函数只写"要做什么、读什么字段、写什么字段"，具体表达式全部引用第五节常量，不要在函数体里出现裸数字。

### 2. `settleQuota(state)`
- 若 `state.day === state.quota.nextArrivalDay`：
  - `arrival = QUOTA_PER_PERIOD - state.quota.pendingAdvanceDebt * QUOTA_ADVANCE_INTEREST`（利息在到货时扣，扣完清零 `pendingAdvanceDebt`，且 `arrival` 不得小于 0）；
  - `state.base.ammo += arrival * QUOTA_COMPOSITION.ammo; state.base.supply += arrival * QUOTA_COMPOSITION.supply;`
  - `state.quota.nextArrivalDay += QUOTA_PERIOD_DAYS;`
  - `state.quota.nextAmount = null`（下一批数字要到提前期才揭示，见 `refreshInfoSnapshot`）。
- 预支：若 `state.orders.advanceQuota > 0`，检查 `advanceQuota <= QUOTA_PER_PERIOD * QUOTA_ADVANCE_MAX_RATIO - state.quota.pendingAdvanceDebt`，通过则立即把 `advanceQuota` 加进 `state.base`（按 `QUOTA_COMPOSITION` 拆分），并累加进 `pendingAdvanceDebt`；不通过则该指令本回合被拒绝并记进 `eventLog`（玩家指令永远不能静默失败）。

### 3. `settleMobilization(state)`
- 若 `state.day === state.personnel.mobilization.nextArrivalDay`：`state.personnel.pool += state.personnel.mobilization.nextAmount`（数量数值起点未给具体每批数字，暂定 = `DIVISION_SAFE_RESERVE_DAYS` 换算出的满编点数的一个固定比例，实现时先给一个占位数，标记 TODO，交给试玩调），`nextArrivalDay += MOBILIZATION_INTERVAL_DAYS`。

### 4. `advanceQueues(state)`
- `transitQueue`：每批 `arrivesDay === state.day` 的，按 `lineId` 的 `via` 生成一条战报文案（"车队经过中转站…"，纯文案不影响数值），然后：若目标师所在防区已丢失/战线后退到该批次送不到（demo 简化：只在 `resolveBattles` 判定"战线后退"事件时，把当天所有仍在途且目标是该师的批次标记 `lost = true`，在这一步遇到 `lost` 批次直接从队列移除、计入彻底损失、写日志），否则把 `cargo` 加进对应师的本地储备（见下"到货换算"）；从队列移除。
- `trainingQueue` / `hospitalQueue`：同样按 `arrivesDay` 结算，训练完的进入"待分配的人员池"（不是自动回原师，见机制库「人员的独立环路」——回收老兵不自动归队）；医院超过 `HOSPITAL_DAILY_QUOTA_RATIO` 换算出的当日名额时，超出部分 `arrivesDay += 1` 并标记 `overflowDays += 1`，`overflowDays > 0` 的那部分按 `HOSPITAL_OVERFLOW_DEATH_MULT` 结算死亡（从队列里扣除相应人数，计入彻底损失）。

**到货换算**：一批 `cargo.ammo`（单位 D）到某师后，`division.ammoDays += cargo.ammo / dailyConsumptionOf(division)`；`dailyConsumptionOf` 是"该师当前姿态下的日消耗"（见 5d），这样"天数"这个抽象单位才能在"D"和"天"之间来回换算而不引入第二套单位。

### 5a. `perceive(state, division)`
- 生成 `division.perceivedSelf`：把真实的五个数（满编率、弹药天数、给养天数、疲劳、装备）按 `1 - personality.selfAwareness` 的幅度加一个偏差（demo 不用骰子，用一个确定性偏移：偏差方向由"该师上一次决策是否判断正确"决定，或最简单的暂定实现——固定偏移 `trueValue * (1 - selfAwareness) * 0.3` 的正向乐观偏移，即自知力低的师总是觉得自己比实际状况好一点，与机制库"不是撒谎，是误判"一致）。这是本文件的暂定实现，标记见十一。

### 5b. `decidePosture(state, division)`
严格照抄 `机制库.md` 系统 5 的规则表，逐条判断，命中即返回，不要重排顺序：

```
若 弹药 < 2 且 未接敌            → dormant
若 弹药 < 1 且 接敌              → retreat（除非收到死守命令）
若 疲劳 > 阈值                   → 申请 refit（阈值暂定 0.75，试跑调）
若 有进攻命令 且 储备 ≥ 门槛     → attack（门槛 = 该师 aggression 换算出的天数，见下）
若 有进攻命令 但 储备不足        → 按 obedience 决定：obedience 高→硬上 attack；低→拖延（本回合仍是上一姿态）
若 储备充裕 且 判断敌方薄弱      → 按 aggression 判断自作主张 attack（demo 简化："判断敌方薄弱"＝固定小概率但不用骰子，改成一个确定性条件：连续 2 天未接敌且储备 ≥ 安全线的 1.5 倍）
否则                             → defend
```
用的是 `division.perceivedSelf`（他自己以为的状态），不是真实状态——这一条决定了"误判"能不能生效，别写错成读真实值。

### 5c. `generateRequest(state, division)`
- `baseNeed = dailyConsumptionOf(division) * 若干天缓冲`；`inflatedNeed = baseNeed * (1 + hoarding) * (共用运力时的抢运力加成)`。抢运力加成的具体实现：demo 简化为——若同一运力池上还有其他师，`inflatedNeed *= 1 + hoarding * 0.3`（"共用运力"的效果就是这个加成会挤占 `dispatchShipments` 里的优先级计算，不需要单独建模"抢"这个动作，见步骤 7）。
- 这份请求只用于 UI 展示"该师申报的需求 vs 真实需求"的落差（供玄家判断"谁在虚报"），不直接决定发多少——发多少由步骤 7 的玩家指令决定。**这是"只能改变处境，不能替他决策"的落地点：请求只是信息，不是指令。**

### 5d. `consumeAndApplyPosture(state, division)`
- `mult = POSTURE_CONSUMPTION_MULT[division.posture]`；
- `ammoConsumed = mult.ammo * ammoTierOf(division).combatMult`（**注意**：弹药消耗本身也要乘弹药档位——"部队打不出它没有的炮弹"，档位低时消耗和战斗力一起降，见机制库系统 4）；
- `supplyConsumed = mult.supply`（给养消耗不受弹药档位影响）；
- 若当天有交战（由 `resolveBattles` 提前标记 `division.underAttack`，注意步骤顺序：5d 在 6 之前跑，所以"是否接敌"要用**上一天**留下的 `underAttack` 状态，或者把交战判定拆成"预告 + 结算"两次，demo 简化为用"上一天"的标记，这一处顺序上的先后关系是本文件对九步顺序的必要澄清，不算改动设计）：额外加 `SPIKE_EXTRA_DAYS_EQUIVALENT` 等效的尖峰消耗；
- `division.ammoDays -= ammoConsumed / DIVISION_SAFE_RESERVE_DAYS`（换算见常量表说明）；`division.supplyDays` 同理；
- 给养连续低于阶梯下限则疲劳与非战斗减员按机制库「给养 ↔ 人员正反馈」累加（`fatigue += x`，`manpowerRatio -= y`，`y` 部分直接计入彻底损失，不进回流）。
- `fatigue` 按姿态在 `refit` 时快速下降，其余姿态缓慢上升，具体曲线数值起点未给，暂定线性，标记见十一。

### 5d'. `autoAllocateArrivedCargo` / 步骤 6 里的战斗减员分流、`dispatchShipments`
这两块直接对应机制库系统 5「前线自行分配」与系统 4「黑箱」，实现要点：
- **前线自行分配**：本师收到的弹药，若师姿态是 `attack` 且 `hoarding` 低，允许把一部分"给养余量"挪用为弹药的等效消耗抵扣（demo 简化实现，制造"送去的东西被以你预料之外的方式花掉"的体验）——**这条如果第一版实现起来复杂度过高，可以先跳过，只保留文案（战报里写"部分给养被挪用支援攻势"），下一版再接数值**。跳与不跳都要在 `eventLog` 里显式写清楚，不要悄悄丢机制。
- **战斗黑箱** `resolveBattles(state)`：只在 `underAttack` 为真（由 `battlePreview` 提前 3 天标记）的师上跑。规则：双方效能比决定战线移动方向/距离/双方损失，效能公式见第五节。产出：`division.frontMovement`（demo 只需要一个标量：正数=前进，负数=后退，不需要真的挪动地图坐标，UI 上用文字描述"战线后退 X 公里"即可，因为界面不是地图是监护仪，机制库「摄像机跟着物资走」）；`casualties`（按 `CASUALTY_SPLIT` 分 `kia`/`wounded`，`wounded` 进 `hospitalQueue`，`kia` 直接从 `manpowerRatio` 扣除且不进任何队列）。
- **少用或不用骰子**：效能比到"移动多少/损失多少"的映射用一个确定性的分段函数（比如效能比 ≥1.5 → 大胜；1.0~1.5 → 小胜；0.7~1.0 → 小败；<0.7 → 大败，各档对应固定的移动距离与损失比例区间的**中值**，不掷骰子取具体值），符合尺子 4。

### 8. `generateDailyReport(state)`
- 每个有事件（交战/姿态变化/批次到达/queue overflow）的师生成一段文字，模板抄 `机制库.md` 系统 4 的战报示例句式（"第三师于 K12 遭遇进攻。弹药于交战第二日耗尽…"）。
- **反事实提示**的实现：把"如果把某一天发给师 A 的批次改发给师 B"这个改动应用到一份状态快照上，重跑一遍 `consumeAndApplyPosture` + `resolveBattles`，比较结果差异，挑一句最大的差异生成提示句。**只在发生了"守不住/差点守不住"的战斗后触发**，不用每天都算，省性能也省实现量。

### 9. `refreshInfoSnapshot(state)`
- 按 `INFO_DELAY_DAYS` 把 `state.day - delay` 那天的师状态拷贝一份存进 `division.lastReportSnapshot`，UI 只读这份快照，不读实时状态（除了"基地库存"字段——数值起点明确写"基地库存对玩家完全透明、精确、无延迟"，这是唯一不走延迟快照的字段）。
- 更新配额预告：`state.day + QUOTA_PREVIEW_LEAD_DAYS === state.quota.nextArrivalDay` 时把 `nextAmount` 从 `null` 换成真实值。

## 七、玩家指令 → UI 收集流程

`Demo 切割线.md` 三、命令：玩家每天能做的只有五件事，全部写进 `state.orders`，UI 侧不需要"确认发车"按钮——**没有手动发车**，玩家改的是规则，`dispatchShipments` 每天自动按规则执行：

| 命令 | 对应 `orders` 字段 | UI 控件（暂定） |
| --- | --- | --- |
| 1. 调整线路配比 | `lineRatios` | 每条线三个滑条（弹药/给养/人员），归一化到合计 1 |
| 2. 调整师优先级 + 训练档位 | `divisionPriority`、`trainingTrack`、`personnelAssignment` | 每师一个优先级数字输入 + 训练档位单选 + 人员分配数字输入 |
| 3. 设置最低储备线 | `minReserveDays` | 每师一个数字输入（天） |
| 4. 回电告知真相 | `briefTruth` | 每师一个勾选框 |
| 5. 今日发运上限 + 是否预支 | `dailyShipmentCap`、`advanceQuota` | 一个数字输入（默认 = 当前总运力）+ 一个预支数量输入 |

**每天一次"推进"按钮**调用 `advanceDay(state)`，之前玩家可以随意改 `orders` 里的值，改了立即体现在下一次推进（不需要"提交"这个中间态，`orders` 本身就是当前生效的规则，直到玩家再改）。

## 八、监护仪面板字段映射（`logistics-ui.js` 要渲染的东西）

对应 `Demo 切割线.md` 三、界面：

## 十一、实现时的模糊点与暂定选择（供审查）

设计文档已经把"为什么"讲得很清楚，但落到代码时有几处需要一个具体数字或具体单位，原文没有给到这个精度。以下每一条都是本文件替设计文档做的补充决定，不是新机制，纯粹是"把话说到能编译的精度"。如果试玩后发现不对，只改这里、改常量表，不用回头怀疑机制本身：
